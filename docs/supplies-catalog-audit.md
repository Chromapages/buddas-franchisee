# Authorized Supplies Catalog audit and implementation

## Existing component tree

RootLayout → PortalLayout (session/permissions, authorized locations, streamed counts) → PortalProvider → PortalShell → SuppliesPage → PortalDataBoundary → Suspense/CatalogFallback → CatalogModule → CatalogBrowser → product cards and existing cart server action.

Product links open `/portal/supplies/[slug]`. Cart is `/portal/cart`, review is `/portal/checkout`, durable confirmation is `/portal/checkout/confirmation`, and prior order history is `/portal/orders`.

## Files and dependencies

- `src/app/portal/supplies/page.tsx`: VIEW_CATALOG check, concurrent product/cart loads, page heading and module fallback.
- `src/components/portal/catalog-browser.tsx`: local React search/category/pending state, Next product links/images, add server action, PortalProvider count updates.
- `src/app/portal/supplies/[slug]/page.tsx`: unit-scoped product lookup by slug and specification detail; no new product endpoint is needed.
- `src/components/portal/portal-shell.tsx`, `src/features/portal/portal-context.tsx`: active-unit identity, authorized selector, cart count, five mobile destinations.
- `src/features/auth/session.ts`, `authorization-server.ts`, `authorization.ts`: verified Firebase session plus role and managed-unit checks. Real roles are franchisee and admin; corporate identities are separate.
- `src/features/portal/types.ts`: PortalProduct contains category, SKU, price, boolean isAvailable, leadTimeDays, packSize, optional imageUrl. No stock quantity, reservation/allocation, separate order-unit, fees, currency field or price-as-of timestamp.
- PortalLocation and PortalProduct do not define a warehouse or fulfillment-source relationship. The Supplies header therefore identifies only the authoritative working-unit catalog, price, and availability scope; it must not infer a warehouse label.
- `storage-adapter.ts`, `firestore-storage.ts`, `db-storage.ts`: current adapter selection and reads. Firestore catalog is `units/{locationId}/products`; SQL adapter supplies unit pricing. Explicit local seed mode currently replaces the whole adapter, including location records and orders, not just products.
- `cart.ts`, `cart-actions.ts`, `cart-policy.ts`: HttpOnly, SameSite=Lax cart cookie stores SKU/quantity by authenticated user and unit for seven days. Legacy unit-only entries migrate into the current user envelope. Current products are read server-side for availability/pricing.
- `actions.ts`, `checkout-review.ts`, checkout page/form: CREATE_ORDER, target-unit confirmation, authoritative cart recalculation and fingerprint review before acceptance. Current acceptance still assigns a fixed ETA and short random references; these are financial-integrity follow-ups.
- `src/lib/analytics.ts`: existing operator allow-list transport; no query text, product IDs or prices should be sent.
- `operator-mobile.css`, `operator-home.css`, `globals.css`: cream/teal palette, Poppins/DM Sans, panel/button styles, focus system, safe area and measured bottom-nav clearance. Existing server error boundary and Next Suspense are reused.

## Limitations and findings

- Categories were hardcoded to three although the type also supports Equipment. Derive chips from actual authorized products.
- Search is local case-insensitive name/SKU substring matching. Trim the actual query before matching.
- The catalog currently contains only SKU, name, category, pack information, lead time, availability, price, and optional image URL. There is no supplier/manufacturer, alias/synonym, or remote search contract. The mobile lookup therefore performs a deferred local search across SKU, exact/partial product name, and category; it sends no query over the network, so there are no stale search requests to cancel. Exact SKU matches rank before exact names, prefixes, category matches, and partial matches. Recent authorized order items break ties only within the same relevance tier.
- Catalog filtering is now split into reusable `CatalogToolbar`, `CategoryDrawer`, `FilterDrawer`, `SortSheet`, and `AppliedFilterChips` components, backed by `catalog-filtering.ts`. Quick views are restricted to actual categories plus Recent only when current-unit order history exists; All resets the query and every filter to the complete authorized catalog. The modal controls use native `<dialog>` sheets: category, boolean availability, recent-order history, and lead-time ranges are available; low stock, backorders, suppliers, aliases, ratings, and “on order guide” filters are intentionally absent because the model cannot support them. Sort options are relevance during active search, recent ordering, name, price, availability, and lead time.
- Catalog results use compact `ProductOrderRow`-style records rather than consumer cards. The linkable product-information region holds the optional image, name, SKU, conditional category, pack facts, availability, lead time, and a recent-order flag only when present. Price and Add/quantity controls are siblings of that link, preventing cart interaction from navigating to details. The model cannot determine “in stock,” a named order unit, or last-order timestamps, so rows use the exact supported language: Available to order, listed pack, business-day lead time, and Recently ordered.
- Purchasing defaults to a single Add action. Once server acceptance returns, the same row renders the authoritative current pack count with `−`, direct numeric entry, and `+`. Direct entry accepts only whole values from 0 through `MAX_CART_QUANTITY` (currently 100); Enter or blur commits the value, 0 removes the item and restores Add, and invalid drafts revert with a concise announcement. Cart count is updated from the server response; no optimistic cart write is used. The server action also validates integer/range, active unit, product availability, and current price, while the client’s in-flight guard prevents duplicate/racing mutations.
- The shared portal header remains the global compact cart indicator. Supplies adds a fixed mobile order-summary dock only when the active unit has cart items; it shows quantity, server-priced subtotal, pending-save state, and View cart. The dock is positioned above the measured bottom navigation with focused-control clearance and no empty-cart placeholder. Cart cookie records remain partitioned by authenticated user and unit. When a user switches units with a nonempty cart, the old cart stays stored under the previous unit and the destination Supplies page receives a short-lived explicit notice that nothing was moved or discarded.
- Formal product-state audit: the current system supports only `AVAILABLE` and `NOT_AVAILABLE_FOR_LOCATION`, derived from unit-scoped `isAvailable`. There is no source for low stock, backorder, discontinuation, replacement, substitute approval, or order-window states; those are not rendered. Firestore catalog reads now include authorized unavailable products so operators can see the SKU and its explicit non-orderable status. Cart mutations resolve current availability and price server-side; checkout rejects carts with unavailable items. The cart records price and pack-size snapshots at accepted add/quantity updates, then shows an explicit cart warning when a current catalog price or pack differs from the saved snapshot. The review fingerprint remains the final pre-acceptance price check.
- Supplies authorization uses server-side `VIEW_CATALOG`, `VIEW_WHOLESALE_PRICING`, `MANAGE_CART`, `CREATE_ORDER`, and `VIEW_ORDERS` capabilities. Current real roles have the established access set; components consume a shared capability object so a future restricted role does not need a separate Supplies implementation. See `docs/supplies-authorization-audit.md` for the enforcement map and intentionally absent capabilities.
- Supplies accessibility pass: semantic search, one H1, labelled native sheets, 44px-plus target checks, keyboard Escape/focus restoration, status announcements, sticky-dock focus clearance, color-independent availability states, and 200% reflow checks are recorded in `docs/supplies-accessibility-audit.md`. VoiceOver/TalkBack remains a device-only follow-up.
- Supplies Bakery Counter mode is codified in `docs/supplies-bakery-counter-design.md`: Cream canvas, white functional rows/docks, Dark Teal structure and primary actions, Base Teal recognition, Cocoa operational copy, Poppins hierarchy, DM Sans utilities, and no decorative or promotional treatment.
- Supplies purchasing analytics now uses the existing allow-listed Operator Workspace transport. The event plan, readiness score, privacy boundaries, and downstream limitations are documented in `docs/supplies-analytics.md`.
- Bakery Counter brand mode is documented in `docs/supplies-bakery-counter-design.md`: Cream canvas, white dense surfaces, Dark Teal structure/actions, Base Teal recognition only, Cocoa metadata, Poppins hierarchy, DM Sans utility text, and no normal-action Orange or off-palette success green.
- Replenishment audit: `getOrdersByLocation(locationId)` exposes prior unit-scoped order lines, their order timestamp, and ordered quantity. It does not expose templates, saved lists, favorites, approved order guides, standard quantities, item-level last-order records, or recommendation signals. Supplies now derives a Recently ordered layer from non-cancelled orders only: last ordered date, last quantity, and Frequently ordered when the same SKU appears in more than one recorded order. The layer is omitted for valid empty history; SLC’s current authorized response is one such empty-history case. No Lists/Order Guide destination has been added because no list backend exists.
- Product detail pages now separate list-level choice from purchase confidence: name/SKU/category, verified visual or category placeholder, availability, wholesale price, pack/order unit, lead time, description, server-scoped purchase history when present, and a persistent mobile purchase dock. Category modules are supported through `supplyDetails` for ingredient handling/storage, packaging dimensions/material/count/compatibility, uniform size/fit/details/placement, and signage dimensions/application/artwork/installation. Current catalog records do not contain these fields, related products, substitutes, or authorized product-document references, so those modules and sections remain absent rather than fabricating content.
- All records load in one request; filtering is client-side and there is no pagination. This is appropriate for the current small fixture set; do not invent backend pagination without volume evidence.
- No shopping-list, favorite, saved-cart template or reorder-from-history workflow was found. Orders saved views are not shopping lists.
- `imageUrl` alone is not evidence that an asset represents a SKU. The UI now renders an image only for a `/images/catalog/` asset with exact identifying alt text and `imageVerified: true`; otherwise it uses a product-class placeholder. Local fixtures have no SKU image assignments, and the prior CLI default that substituted a consumer bakery image has been removed. See `docs/catalog-image-policy.md`.
- Inventory allocation copy overstates the boolean availability model. Replace it with approved-products/current-unit copy.
- Availability is enforced server-side but was not exposed in the cards. Disable unavailable and invalid-price products with clear text.
- Add errors were uncaught; one pending request changed every button label. Keep pending feedback per SKU, prevent duplicate submissions and report generic recoverable errors without leaking exceptions.
- Category selection lacked aria-pressed; product buttons had identical accessible names; no filter reset existed. Add state, named actions, and reset without moving focus.
- Cart count was duplicated in local state and became stale after navigation/refresh. Reuse PortalProvider counts.
- Mobile images/card nesting consume scan space. Use compact image thumbnails, prominent product name/SKU, pack/lead-time lines, price plus add action, and an existing detail link for expanded description.
- Active unit can change in another tab before an add request. Bind the displayed unit to the add action and compare against the authoritative session before writing.

## Implementation sequence

1. Fix search/category derivation, availability/price guards, local error/success feedback, duplicate-add protection, accessible chip/button states, and shared cart counts.
2. Bind catalog adds to the displayed unit and reject mismatch on the server. Keep the same server action and cookie architecture.
3. Apply compact mobile-only card geometry, wrapping metadata and controls; keep description available in product detail. Remove inappropriate seed food imagery from catalog fixture records.
4. Correct unsupported inventory-allocation language, display a development seed notice, and avoid false loading zeros when cart data fails independently.
5. Verify the existing demo Firebase login, catalog search/reset, detail navigation and narrow/large-text layouts. Report any live-provider or checkout limitations explicitly.

## Scope

No API/state-library replacement, product schema migration, invented stock counts, favorite workflows or persistent financial caching. Desktop retains its grid and full description; shared correctness and accessible names improve on both surfaces.

## Implemented and verified

Implemented the sequence above in the existing CatalogBrowser, Supplies page/detail, cart server action, mobile stylesheet and local product fixtures. The mobile information architecture is now an Operator Order Guide: an explicit canonical working-unit catalog scope; a sticky, first-class SKU/name/category lookup; exact-SKU labels and relevance-first ordering; a compact quick-filter row; scalable category/filter/sort bottom sheets; removable applied-filter chips; compact scanning rows with detail links separate from cart controls; genuine recent-order shortcuts when history exists; product count; quantity-in-list; and a persistent current-order summary. The no-result state repeats the search query, keeps the sticky Clear search affordance visible, offers filter removal, and exposes actual category fallbacks. Search/filter state persists per active unit in browser session storage, including after a quick product-detail round trip or server-action refresh. The header states that catalog prices and availability apply to the named unit and omits a fulfillment source because the current model has none. The shared shell remains the sole location selector. Its authorized switch action updates the active unit, revalidates the portal layout and route, and remounts the location-keyed catalog and count context; carts remain partitioned by unit in the existing cart cookie. The add action rejects mismatched displayed units, invalid authoritative prices, and an already-reached quantity limit. Failed cart-count and order-history reads no longer collapse the catalog. Client feedback is politely announced where the mounted tree is retained, while the persistent cart summary provides durable confirmation after a route refresh. Category selection uses aria-pressed plus a checkmark. No raw exception payload is displayed.

Browser verification uses `scripts/verify-demo-operator-login.py` and the existing demo Firebase account. Confirmed: login and session exchange; the current authorized catalog count (fixture-independent); category drawer selection with a visible checkmark; filter-sheet apply count; sort-sheet selection; individually removable applied filters and Clear all; padded exact SKU search returning an explicit exact-match label; category-term search; query persistence after cart refresh and product-detail Back navigation; recoverable no-result state with query, Clear search, filter removal, and category fallback; sticky search reachability while browsing; Add-to-cart success; direct numeric quantity entry; invalid integer recovery; zero-quantity removal returning the row to Add; header cart count and fixed active-order summary with subtotal; persistent cart count; product-detail navigation; at least 44px quick-filter, toolbar, quantity, save and cart-summary targets; and no document horizontal overflow at 320/430/1280px or doubled root font size. Screenshots are captured in `design-qa/`. The test cart is confined to the disposable browser context. No order was submitted.

The local demo session uses the explicit in-memory storage flag. Production Firestore rejection, simultaneous cross-tab cart writes, provider outages, genuine stock changes, remote image-host configuration and shipping/tax/ETA accuracy were not validated end-to-end. Fixed acceptance ETA and short random invoice/order references remain separate security/fulfillment follow-ups. Production catalog still has no server pagination or stock quantities. No additional vendor, library, API or persistent collection was introduced.
